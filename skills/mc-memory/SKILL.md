# mc-memory · 品牌记忆管理

## 触发条件

- "查看品牌记忆" / "品牌记忆是什么" / "品牌积累了什么"
- "记住这个洞察" / "保存这个发现" / "更新品牌记忆"
- "brand memory" / "memory" / "品牌积累"
- "切换品牌 {slug}" / "初始化品牌记忆"

---

## 文件路径规则

| 场景 | 路径 |
|------|------|
| 单品牌（默认） | `memory/brand-memory.md` |
| 多品牌 | `memory/{brand-slug}/brand-memory.md` |
| 品牌 slug 来源 | 当前 campaign 的 `brief.md` 中 `brand:` 字段；未指定时使用默认路径 |

---

## 操作清单

| 用户意图 | mc-memory 执行 |
|---------|---------------|
| 查看 | 读取 brand-memory.md，输出格式化摘要（不输出原始 markdown） |
| 手动添加洞察 | 将用户提供的内容追加到对应章节 |
| 手动修正 | 根据用户指令更新或删除某条记录 |
| 切换品牌 | 读取指定 brand-slug 的 brand-memory.md |
| 初始化 | 为新品牌创建空模板（`memory/{slug}/brand-memory.md`） |

## 诊断记忆章节

除品牌智慧外，brand-memory.md 还可包含 `## 诊断记录` 章节，由 mc-diagnose 自动写入。格式：

```markdown
## 诊断记录

### {YYYY-MM-DD} — {诊断模式}
**症状：** {一句话}
**根因：** {一句话}
**修复状态：** 待执行 / 执行中 / 已修复 / 复发
**关联技能：** mc-{skill}
```

mc-diagnose / mc-analytics / mc-dashboard 在执行时自动读取此章节，避免重复排查已知问题。

用户说"更新诊断状态"时，mc-memory 将对应条目的修复状态改为用户指定的值。

## 写回规则

每次写入前，读取目标章节内的现有条目，把新内容和它们逐一比对，判定为以下四态之一——不再是"只追加"，让 brand-memory.md 能自我修正而不是无限堆积可能已经互相矛盾的旧记录：

| 判定 | 触发条件 | 动作 |
|------|---------|------|
| **新增** | 新内容与本章节任何现有条目都不同主题 | 追加为新条目 |
| **更新替换** | 新内容与某条现有条目同主题（如同一诊断症状、同一品牌定位判断），但结论不同 —— 新证据/新一轮诊断推翻或修正了旧结论 | 追加新条目，**同时在旧条目末尾加一行 `⚠️ 已被 {新条目日期} 的记录取代，见下方`**（不物理删除旧文字——保留人工可 git diff 追溯的历史，只做标记，不做覆盖） |
| **标记过期** | 旧条目所述问题/状态已确认不再适用（如"诊断记录"里某症状的修复状态被标记"已修复"且超过一个 campaign 周期未复发） | 在该条目末尾追加 `📌 状态：已过期`，条目本身保留在文件中不删除 |
| **跳过重复** | 新内容与某条现有条目语义相同（含原有的 slug 去重 / 日期+症状去重规则） | 跳过，不写入 |

具体去重/冲突判定规则：
- `## Campaign 历史` 按 campaign slug 判定：同一 slug 已有记录 → 跳过重复（除非新记录明确是"更新"该 campaign 的复盘结论，此时走"更新替换"）
- `## 诊断记录` 按日期 + 症状判定：同一天同一症状 → 跳过重复；不同日期但**同一症状、根因判断不同** → 更新替换（旧根因判断可能是错的，不能悄悄保留误导后续技能）
- 内容语义相同的品牌洞察 → 跳过重复
- 文件不存在时自动创建空模板后写入，本轮写入视为"新增"

**为什么不直接覆盖或物理删除**：brand-memory.md 是纯 markdown、人可以直接打开和 git diff 的文件——这是它相对于向量数据库类记忆系统的真实优势。"更新替换"和"标记过期"都只追加标记行，不删除旧文字，保留完整历史的同时让读者（包括下一次读取此文件的技能）能一眼看出哪条结论已经不作数。

## 文件分层与压缩

只追加不压缩的文件会一直变长。mc-cmo 每次对话都要加载品牌上下文，一个跑了两年、三十个 campaign 的品牌，brand-memory.md 会长到把上下文预算吃掉一大块——而其中真正每次都需要的，只有最上面那一小块。

### 两层结构

| 层 | 内容 | 加载策略 | 目标体量 |
|----|------|---------|---------|
| **常驻层**（文件顶部） | 品牌定位、人格、语调红线、当前主推产品、已验证的核心洞察 | mc-cmo 每次全量加载 | **不超过 100 行**，超了必须压缩 |
| **档案层**（常驻层之后） | Campaign 历史、诊断记录、历史洞察、已标记过期的条目 | 按需加载：技能明确需要历史时才读，或用户主动问"以前做过什么" | 不限长度 |

文件里用一条固定分隔标记两层，供技能判断读到哪为止：

```markdown
# {品牌名} · 品牌记忆

## 品牌定位
## 品牌人格与语调红线
## 当前主推
## 已验证的核心洞察

<!-- ARCHIVE BELOW · 常驻层到此为止，以下为档案层，按需加载 -->

## Campaign 历史
## 诊断记录
## 历史洞察（含已过期）
```

### 压缩规则

常驻层超过 100 行时执行压缩，**压缩只发生在常驻层，档案层永不压缩**（它就是用来存原始记录的）：

1. 常驻层里标了 `📌 状态：已过期` 或 `⚠️ 已被…取代` 的条目，整条移到档案层对应章节末尾——**移动不是删除**，原文一字不改。
2. 同一主题的多条洞察合并成一条，并在合并结果后标注来源：`（合并自 2026-03-12 / 2026-05-04 两条记录，原文见档案层）`，原始两条移入档案层。
3. "已验证的核心洞察"只保留仍在指导当前决策的条目；已经落地成品牌定位一部分的洞察，其使命已完成，移入档案层。
4. 压缩后在文件顶部记录：`最近压缩：{日期}，常驻层 {N} 行`。

**压缩纪律：**
- 压缩前先确认档案层已完整承接被移出的内容，再从常驻层删除——**顺序不能反**，否则一次中断就会永久丢失记录。
- 压缩是有损操作中风险最高的一步，因此只做"移动"和"合并"，不做"总结改写"。改写会悄悄丢掉当时的具体措辞和数字，而那些细节往往正是几个月后需要回看的东西。
- 单品牌记忆文件本身不设总量上限——档案层再长也不影响每次对话的加载成本，没有删除历史的理由。
