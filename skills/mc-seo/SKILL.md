## 优先级判定规范（全技能统一）

本技能多张表都有"优先级"列——关键词地图、技术审计、外链路线图。它们统一按 **影响面 ÷ 执行成本** 定档，不是凭手感排序。SEO 团队拿到清单第一件事就是问"先做哪个"，所以优先级和"这事有多严重"必须分开写：一个严重但要三个月的问题，排序上应该输给一个中等严重但今天就能改完的。

| 档位 | 判定 | 含义 |
|------|------|------|
| **P0** | 高影响 + 低成本 | 本周做完。典型：robots.txt 误屏蔽、首页 title 缺失、已有排名第 4-10 的关键词做页面微调 |
| **P1** | 高影响 + 高成本 | 排进本季度，需要排期和资源。典型：站点结构重构、Core Web Vitals 大改、核心品类页内容重写 |
| **P2** | 低影响 + 低成本 | 顺手做，或打包批量处理。典型：图片 alt 补全、次要页面 meta description |
| **P3** | 低影响 + 高成本 | 明确记录为"暂不做"，写清楚重估条件（如"等品类页流量到 X 后再评估"），不要留在清单里反复占用注意力 |

**各表的"影响面"分别指什么：**

| 表 | 影响面 = | 执行成本 = |
|------|---------|-----------|
| 关键词地图 | 机会分 = 搜索量 × 可赢性 × 商业相关性。**可赢性**：当前排名 4-10 最高（临门一脚），11-30 次之，未收录或 >50 最低；竞争度高则降档。**商业相关性**：交易型意图 > 商业调研型 > 信息型 | 内容生产量 + 是否需要新建页面 + 是否依赖外链才能进前三 |
| 技术审计 | 是否阻断收录（阻断类一律高影响）> 是否影响全站 > 是否只影响个别页面 | 是否需要开发介入、是否涉及架构改动、是否需要停机 |
| 外链路线图 | 目标链接的域名权重 × 相关性；已有"执行难度"和"时间周期"两列，直接作为成本输入 | 直接读该表的执行难度 + 时间周期 |

## 数据置信分级

搜索量、竞争度、域名权重、Core Web Vitals 实测值都依赖第三方工具（Ahrefs / Semrush / 5118 / GSC / PageSpeed Insights）。当前环境未必接得上这些工具，**填进表格的数字必须让读者一眼看出是实测还是推的**——一张分不清来源的审计表，会让团队按估算值去承诺排名。

| 级别 | 含义 | 标注 |
|------|------|------|
| 实测 | 来自工具或平台直接读数（GSC 的展现/点击、PageSpeed 实测分、Ahrefs 的 DR、站点实际 HTTP 状态码） | `[实测·{工具名}]` |
| 三方估算 | 来自第三方工具的估算值或行业报告（工具给的"月均搜索量"本身就是估算，不是真实值） | `[估算·{来源名}]` |
| 推断 | 由搜索结果页观察、可比关键词、竞品页面结构间接推算 | `[推断]` |

**硬规则：**
- `[推断]` 级数字只能用于方向性判断（有没有机会、大概什么量级），**不能作为排名承诺、流量预测或预算申请的依据**。
- 整表都是推断时在表头写明，不要逐格标注制造"部分实测"的错觉。
- 关键决策数字（核心词搜索量、竞品外链总量）需 ≥2 个独立来源；来源冲突时输出区间而非单值。
- 无任何工具可用时不要跳过审计——用搜索结果页能观察到的事实（是否收录、title 是否合理、有无结构化数据摘要）照常做，只是全表标 `[推断]`。

## 模块 1：关键词研究与策略

### 关键词分层框架

**层级 1：品牌词**
- 品牌名 + 品牌名变体（拼写错误、缩写）
- 品牌名 + 产品名
- 品牌名 + 竞品对比（"品牌 A vs 品牌 B"）
- 策略：防守为主，确保品牌词排名第一，拦截竞品抢占意图

**层级 2：品类核心词（行业词）**
- 高搜索量、高竞争度
- 转化意图强（商业意图 / 购买意图）
- 策略：长期耕耘，需要强域名权重和持续内容投入

**层级 3：问题词 / 场景词**
- "XX 怎么选" / "XX 和 XX 的区别" / "最好的 XX"
- 搜索意图清晰，内容可精准匹配
- 策略：内容营销驱动，博客/指南为主要载体

**层级 4：长尾词**
- 低搜索量、低竞争度、高转化率
- 具体场景化（"适合敏感肌的无香料面霜"）
- 策略：产品页和集合页优化，快速出排名

### 关键词评估维度

```markdown
|--------|-----------|----------------|---------|---------|---------|--------|
```

| 商业调研型 (Commercial) | "最好的 XX" / "XX 评测" / "XX 对比" | 对比页 / 评测内容 / 品类指南 |
| 交易型 (Transactional) | "买 XX" / "XX 价格" / "XX 优惠码" | 产品页 / 集合页 / 落地页 |

## 模块 2：页面 SEO（On-Page SEO）

### 核心优化清单

**标题标签 (Title Tag)**
- 长度：50-60 字符（Google）/ 30-50 字符（百度）
- 包含核心关键词（尽量靠前）
- 对用户有吸引力，体现差异化价值
- 每个页面唯一，不重复

**Meta 描述 (Meta Description)**
- 长度：120-160 字符
- 包含关键词（关键词会加粗显示在 SERP）
- 有明确的 CTA（号召性用语）
- 对用户有说服力，提高点击率

**标题层级结构 (H1-H6)**
- 每个页面只有一个 H1，包含核心关键词
- H2/H3 覆盖次级关键词和相关话题
- 结构清晰，帮助爬虫理解内容层级

**URL 结构**
- 简短、描述性强（`/skincare/moisturizer-for-sensitive-skin/`）
- 包含目标关键词
- 使用连字符分隔（-），不用下划线（_）
- 避免无意义的参数和数字

**内容优化**
- 首段出现目标关键词
- 语义相关词（LSI Keywords）自然分布
- 内容深度覆盖话题（SkyScraper 原则：比现有排名结果更好）
- 适当的内容长度（以满足用户需求为准，不以字数为目标）

**图片优化**
- Alt 文字描述性且包含关键词（不关键词堆砌）
- 文件名语义化（`sensitive-skin-moisturizer.jpg`）
- 压缩图片，减少加载时间

**内链策略**
- 相关页面之间互相链接
- 锚文字 (anchor text) 含目标关键词
- 孤立页面（orphan pages）接入内链网络
- 将权重从强页面传导给需要提升的页面

### 页面 SEO 审计表

```markdown
| 页面 | Title | Meta描述 | H1 | URL | 内容深度 | 内链 | 综合评分 | 优化建议 |
|------|-------|---------|-----|-----|---------|------|---------|---------|
```

## 模块 3：技术 SEO（Technical SEO）

### 核心技术健康指标

**爬取与索引**
- `robots.txt`：确保不误屏蔽重要页面
- `sitemap.xml`：提交给 Google Search Console / 百度搜索资源平台，及时更新
- 规范化标签 (canonical)：解决重复内容问题
- noindex 标签：只用在真正不需要收录的页面
- 爬取预算：避免无价值页面消耗爬取资源（参数页、过滤页）

**判定规则（robots.txt / sitemap.xml）：**

| 检查项 | Fail | Warn | Pass |
|--------|------|------|------|
| robots.txt | 整站 `Disallow: /`，或误屏蔽了核心页面目录 | 存在但未声明 `Sitemap:` 指令 | 无全站屏蔽，且声明了 sitemap 位置 |
| sitemap.xml | 404 或无法解析 | 能访问但 URL 数量与站点实际规模明显不符（如已知有上千页面但 sitemap 只列了个位数） | 可访问，URL 数量与规模匹配 |

**Staging / 测试子域名误暴露检查**（容易被忽略但影响大——一旦命中会和生产站点抢排名信号）：

- 排查前缀：`test.` `staging.` `dev.` `preview.` `beta.` `uat.`
- **Fail**：该子域名可公开访问、内容与生产站高度相似、且未被认证保护 / `noindex` / `robots.txt` 屏蔽
- **Warn**：子域名可公开访问，但内容相似度或索引保护状态无法确认
- **Pass**：未探测到公开的 staging/test 子域名；或探测到但已被认证、非 200 状态、`noindex` 或 `Disallow: /` 保护
- **影响说明**：Google 可能把 `test.example.com` 和 `www.example.com` 当成两个高度相似但独立的 URL，排名信号被分流，等于自己和自己抢流量
- **修复优先级**：先加 Basic Auth 认证（最快）；其次在该子域名的 `robots.txt` 加 `Disallow: /`；页面仍可被访问到时再加 `noindex`

**Core Web Vitals（Google 页面体验信号）**

| 指标 | 含义 | 优良标准 | 优化方向 |
|------|------|---------|---------|
| LCP（最大内容渲染） | 主要内容加载速度 | ≤ 2.5s | 图片/视频优化、CDN、服务端渲染 |
| FID / INP（交互响应） | 用户点击到响应的延迟 | INP ≤ 200ms | 减少 JS 执行时间、代码分割 |
| CLS（累积布局偏移） | 视觉稳定性 | ≤ 0.1 | 给图片/广告预设尺寸 |

**移动端优化**
- Google 以移动优先索引（Mobile-First Indexing）为默认
- 响应式设计，移动端体验不低于桌面端
- 字体大小、按钮点击区域、视窗设置

**HTTPS 与安全**
- 全站 HTTPS（非 HTTPS 页面在 Google 有排名惩罚）
- 混合内容（Mixed Content）检查

**结构化数据（Schema Markup）**

| Schema 类型 | 适用页面 | 可获得的富媒体摘要 |
|------------|---------|-----------------|
| `Product` | 产品页 | 价格、评分、库存显示在 SERP |
| `Review` / `AggregateRating` | 评价页 | 星级显示在搜索结果 |
| `FAQPage` | FAQ 页 | 问答直接展开在搜索结果 |
| `HowTo` | 教程页 | 步骤列表显示在搜索结果 |
| `BreadcrumbList` | 全站 | 面包屑导航显示在 URL 下方 |
| `Organization` | 关于我们 | 知识图谱信息 |
| `Article` | 博客 | 发布/更新时间显示 |

**JSON-LD 校验：存在 ≠ 合格**

Schema 标签"有没有加"只是第一层检查，更常见的问题是加了但格式错、漏了必填字段、或者语言/URL 对不上页面本身——这些错误肉眼很难在一堆 `<script>` 标签里看出来。按 `@type` 检查必填字段：

| `@type` | 必填字段 | 缺失后果 |
|---------|---------|---------|
| `WebSite` | `name`、`url` | 站内搜索框（Sitelinks Search Box）无法生成 |
| `Organization` | `name`、`url`、`logo` | 知识面板缺失或用错误 logo |
| `Product` | `name`、`image`、`offers`（含 `price`/`priceCurrency`） | 富媒体摘要（价格/库存）不显示 |
| `Article` | `headline`、`author`、`datePublished` | 失去发布/更新时间的 SERP 展示 |
| `FAQPage` | `mainEntity`（每条含 `name`+`acceptedAnswer`） | 问答摘要不展开 |
| `BreadcrumbList` | `itemListElement`（每级含 `position`+`name`+`item`） | 面包屑不显示 |

**判定规则：**
- **Fail**：JSON-LD 无法解析（语法错误）、缺少期望的 `@type`、或必填字段缺失
- **Warn**：推荐字段缺失（如 `Product` 缺 `aggregateRating`）、嵌套字段不完整、多语言页面缺 `inLanguage`
- **Pass**：期望的 `@type` 存在、必填字段齐全、无冲突；多语言页面时 `inLanguage`/`url` 与当前页面语种和地址一致

**多语言站点专项**：每个语言版本应有各自的 Schema，`inLanguage` 与该语言匹配、`url`/`mainEntityOfPage` 指向该语言版本的规范 URL——常见错误是所有语言版本共用同一份英文 Schema，`inLanguage` 全部写 `en`。

**实体 SEO（Entity SEO）**

上面的 Schema 解决的是"这个页面长什么样"，实体 SEO 解决的是更底层的问题：**搜索引擎知不知道"你"是谁**。Google 的排序早已不只匹配关键词，还匹配实体——品牌、产品、作者在知识图谱里是不是一个被识别的对象。这一层做不好，内容再多也只是散落的页面，攒不出品牌权重；这也是 mc-geo 能否被 AI 引擎引用的技术前提（AI 引擎引用的是它"认识"的实体，不是它匹配到的字符串）。

| 动作 | 具体做法 | 验证方式 |
|------|---------|---------|
| **命名一致性** | 品牌名、产品名、公司主体名在全网保持完全一致的写法（大小写、空格、中英文对照）——`XX科技` / `XX Tech` / `XX Technology` 混用会被识别成三个不同实体 | 搜品牌名看 SERP 是否出现知识面板 |
| **实体锚点建设** | 在权威站点建立可被抓取的实体档案：Wikidata、行业目录、Crunchbase/LinkedIn（海外）、百度百科/企查查（国内），信息与官网一致 | 多源信息一致性人工核对 |
| **`sameAs` 关联** | 在 `Organization` Schema 里用 `sameAs` 字段列出所有官方社媒和档案页 URL，把散落的账号显式绑定到同一实体 | 结构化数据测试工具校验 |
| **作者实体** | 内容页标注作者，作者有独立可访问的介绍页（含资历、其他作品链接），而不是只写一个名字 | 对应 EEAT 的 Expertise 信号 |
| **主题聚合** | 围绕核心实体做内容集群（一个支柱页 + 多个子主题页互链），让引擎看到你在这个主题上的覆盖深度 | 站内链接结构审计 |

**与 mc-geo 的分工**：实体建设本身归本技能（它是传统搜索的排序信号）；实体在 AI 搜索引擎中的引用表现和监控归 mc-geo。两边共用同一套实体命名规范——**命名不一致时以 brand.md 为准**，不要各自定义。

**站点结构**
- 扁平化结构（重要页面距首页点击深度 ≤ 3）
- 分页处理（`rel="next"` / `rel="prev"` 或无限滚动的 SEO 处理）
- 重定向链路（避免重定向链/循环重定向）
- 404 页面处理（返回真正的 404 状态码，提供有帮助的内容）

**信任页面可达性（E-E-A-T Trust Pages）**

这里检查的是页面**存不存在、能不能被找到**——纯技术核查，不评判内容质量。内容层面的 E-E-A-T 信号强化（专业背书、权威引用等）见 mc-geo 的对应表格，两者不重复。

| 页面 | 是否必需 |
|------|---------|
| About Us / 关于我们 | 是 |
| Contact / 联系方式 | 是——但不要求独立页面，见下方专项规则 |
| Privacy Policy / 隐私政策 | 是 |
| Terms of Service / 服务条款 | 是 |
| Media / Partners | 否——存在才检查，不存在不算缺项 |

**两层判定（除 Contact 外）：**
- **第一层·存在**：页面 URL 返回 200
- **第二层·可达**：该页面链接出现在 footer 或主导航

| 状态 | 判定 |
|------|------|
| Fail | 页面不存在（非 200） |
| Warn | 页面存在，但未链接在 footer/导航 |
| Pass | 页面存在且可从 footer/导航直接点到 |

**Contact 专项规则**（不要求必须有独立 `/contact` 页面——很多站点合规地把联系方式放在别处）：
1. 先查常见路径 `/contact`、`/contact-us`，200 即视为满足"存在"
2. 没有独立页面时，检查 About 页正文是否含邮箱/社媒/联系方式
3. 再扫首页 footer 和导航是否有 `mailto:`、可见邮箱、社媒链接或联系表单
4. 以上任一命中 → **存在·Pass**；全部没有 → **存在·Fail**
5. 联系方式仅出现在 About 页正文里（不在 footer/导航）→ **可达·Warn**
6. **不要**在 About 页或 footer 已经暴露联系方式的情况下，建议客户"新建一个 /contact 页面"——这是无效建议

## 模块 4：外链策略（Off-Page SEO）

### 外链质量判断标准

**高价值外链特征：**
- 来自高权重、高相关性的网站
- 自然锚文字（品牌词、URL、自然语句）
- 编辑性链接（非付费购买，内容认可）
- 链接位于正文内容中（非页脚/侧边栏）

**低价值/有害外链特征：**
- 来自垃圾网站、链接农场
- 过度优化的精确匹配锚文字
- 隐藏链接、重定向欺骗
- 大量低质量目录站

### 外链获取策略

**1. 数字 PR（Digital PR）**
最高效的白帽外链策略：
- 发布原创研究/调研报告 → 媒体引用时自然获得链接
- 提供行业专家观点给记者（HARO / Qwoted / 国内媒体库）
- 制作可视化信息图，供其他网站转载并引用来源
- 与行业报告机构合作，成为数据来源

**2. 内容营销外链**
- 客座博客（Guest Post）：在行业媒体/权威博客发布原创内容
- 资源页外链：找到"XX 行业最佳资源"类页面，申请收录
- 损坏链接建设（Broken Link Building）：找到竞品/行业失效链接，提供自己的替代内容

**3. 品牌提及转化**
- 监控未附链接的品牌提及（Unlinked Mentions）
- 联系作者要求添加链接（成功率较高，对方已认可品牌）

**4. 合作与联名**
- 供应商/合作伙伴互链
- 行业协会成员页
- 联名活动、跨品牌合作

**5. 社区与论坛（辅助）**
- Reddit、Quora、知乎等平台的高质量回答（通常 nofollow，但带来流量和品牌曝光）
- 行业论坛参与

## 模块 5：内容 SEO 策略

### Topic Cluster 架构

**Pillar Page（支柱页）**
- 覆盖某一大话题的权威综合页（如"护肤完全指南"）
- 内容全面，长度通常 3000-8000 字
- 内链指向所有相关 Cluster 页

**Cluster Content（集群内容）**
- 每个 Cluster 覆盖支柱页的一个子话题（如"敏感肌护肤怎么选产品"）
- 深度聚焦，1000-2000 字
- 全部回链至 Pillar Page

**好处：**
- 提升主题权威性（Topical Authority）
- 内链结构清晰，帮助爬虫理解内容层级
- 避免关键词蚕食（Keyword Cannibalization）

### 内容发布节奏

- **新站**：高频发布，快速建立内容体量和爬取频率
- **成熟站**：质量优于数量，更新老内容 > 新发低质内容
- **内容更新**：定期审查排名下滑内容，刷新数据和案例

## 模块 6：电商 SEO

### Amazon SEO（A10 算法）

**核心排名因素：**

| 因素 | 权重 | 优化方向 |
|------|------|---------|
| 销售转化率 | 极高 | 优化 listing、价格、评论 |
| 关键词相关性 | 高 | 标题、Bullet Points、后台关键词 |
| 点击率 (CTR) | 高 | 主图质量、价格竞争力 |
| 外部流量 | 中 | 品牌网站、社媒引流至 Amazon |
| 评论数量与评分 | 高 | 售后服务、Vine 计划 |
| 库存健康 | 中 | 避免断货导致排名下降 |

**Listing 优化框架：**

```markdown
## Amazon Listing 优化

### 标题（Title）
- 格式：品牌名 + 产品名 + 核心属性 + 规格 + 适用场景
- 长度：移动端前 80 字符最关键
- 包含前 2-3 个核心关键词

### Bullet Points（5 条）
- 第 1 条：最重要的差异化卖点
- 第 2 条：核心功效/成分
- 第 3 条：适用场景/人群
- 第 4 条：规格/使用方法
- 第 5 条：品牌背书/保障

### 后台关键词（Search Terms）
- 250 字节上限（美国站）
- 不重复标题中已有关键词
- 包含竞品词、替代叫法、西班牙语关键词（美国市场）

### A+ Content / Brand Story
- 对话题权威性和外部流量有辅助作用
- 视觉化呈现差异化卖点

### 评论策略
- Vine 计划（新品期获取真实评论）
- Request a Review 功能（买家确认收货后触发）
- 避免黑帽刷评
```

### 独立站 SEO（Shopify / 自建站）

**独立站特有 SEO 挑战：**
- 产品页重复内容（同款不同颜色/规格）→ canonical 标签处理
- 集合页（Collection）分页 SEO
- 用户生成内容（UGC）处理（评论页索引策略）
- 多货币/多语言站点的 hreflang 配置

**高价值页面优先级：**

1. 首页（品牌核心词）
2. 核心集合页（品类词）
3. 高流量/高转化产品页（长尾词）
4. 博客/指南（信息词、问题词）

## 模块 7：国际化 SEO

### Google 国际化 SEO

**技术配置：**
- `hreflang` 标签：告诉 Google 每个页面针对的语言和地区
- ccTLD（`example.co.uk`）vs 子域名（`uk.example.com`）vs 子目录（`example.com/uk/`）
- 建议优先选子目录（复用主域名权重）

**内容本地化（不只是翻译）：**
- 关键词按目标语言重新研究（直译关键词≠本地用户实际搜索词）
- 货币、日期格式、计量单位本地化
- 文化适应性（避免在本地市场有负面联想的表达）

**目标市场 SEO 重点：**

| 市场 | 主搜索引擎 | 特别注意 |
|------|---------|---------|
| 美国 | Google (92%) | Core Web Vitals、E-E-A-T 信号 |
| 英国 | Google (95%) | 英式英语关键词差异 |
| 德国 | Google (95%) | 隐私政策合规（GDPR）、本地托管偏好 |
| 日本 | Google (77%) | 日语关键词研究（和英语搜索行为差异大） |
| 东南亚 | Google 为主 | 移动端优先，低带宽优化 |
| 中国 | 百度 | 单独技术栈，见下节 |

### 百度 SEO

**与 Google SEO 的关键差异：**

| 维度 | Google | 百度 |
|------|--------|------|
| 爬取 | Googlebot | 百度蜘蛛（Baiduspider） |
| 收录速度 | 快（主动 ping） | 慢（需要主动提交） |
| HTTPS | 强烈偏好 | 支持但非决定性 |
| 反向链接 | 极重要 | 重要，但中文链接生态不同 |
| 页面速度 | Core Web Vitals | 速度重要，但标准不同 |
| 内容质量 | E-E-A-T | 原创性、时效性 |
| JS 渲染 | 支持较好 | 支持较差，建议 SSR |

**百度 SEO 操作清单：**
- 在百度搜索资源平台（ziyuan.baidu.com）提交网站和 sitemap
- 使用百度统计（替代 Google Analytics）
- 百度指数做关键词研究（替代 Google Keyword Planner）
- 百度知道、百度百科、知乎、微信公众号内容与网站形成生态联动
- ICP 备案（面向中国用户的网站必须）
- 服务器部署在中国大陆或香港（影响收录速度）
- 避免使用 Google Fonts、Google Analytics（无法在中国加载）

## 真实数据抓取（可选，有站点 URL 时使用）

模块 3 的技术审计表默认靠人工搜索或用户提供数据填写。如果用户给了一个真实站点 URL，可以调用下面两个脚本拿真实数据，而不是靠推断——**能跑就跑，跑不出来就退回置信分级里的 `[推断]`，不要因为脚本失败就整段跳过审计**。

```bash
# 站点级信号：robots.txt + sitemap.xml + staging 子域名暴露探测
node scripts/check-site-signals.mjs https://example.com

# 单页 JSON-LD 结构化数据校验
node scripts/check-schema.mjs https://example.com/some-page
```

两个脚本零外部依赖（只用 Node 内置 `fetch`/`dns`/`net`），输出结构化 JSON，直接对应模块 3 的表格：

| 脚本字段 | 填入哪张表 |
|---------|-----------|
| `robots.status` / `robots.detail` | 技术审计表「爬取与索引」 |
| `sitemap.status` / `sitemap.url_count` | 技术审计表「爬取与索引」 |
| `staging_subdomains.status` / `.public_hosts` / `.detail` | 技术审计表「Staging 子域名」 |
| `schemas[].status` / `.fields_missing` / `.nested_issues` | 技术审计表「结构化数据」 |

**重要限制（如实告知用户，不要假装脚本万能）：**
- 只做静态 HTTP 抓取，不执行 JavaScript——SPA/客户端渲染注入的 JSON-LD 抓不到，会报告"未找到"而不是真的没有。此时提示用户"该站点可能是客户端渲染，建议用浏览器开发者工具查看渲染后的 `<head>`"。
- 部分站点有机器人拦截（返回验证页而非真实内容），此时脚本会如实报告 `error` 状态，不会伪造一个"通过"的结果。
- 有防火墙/私有网络地址会被脚本主动拒绝抓取（SSRF 防护），这是刻意设计，不是 bug。
- PageSpeed / Lighthouse 分数不在这两个脚本范围内（需要用户自备 Google API key，属于可选高级功能，未来再评估是否要加）。

数据置信分级适用：脚本产出的字段标 `[实测·check-site-signals]` / `[实测·check-schema]`；脚本报错或未覆盖的部分（如 Core Web Vitals、内容质量）继续用人工搜索或 `[推断]` 补齐。
